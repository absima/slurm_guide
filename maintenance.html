ADMINISTRATORS / SETUP

The build, in ten steps.

A practical starting sequence, not a universal installation recipe. Adapt the software, identity, storage and scheduling choices to your site.

Administrator guide—not a prerequisite for submitting jobs

If your cluster is already running, use the sequential Everyday use guide. These steps configure shared services and require an agreed maintenance/setup plan.

DEMONSTRATION / THREE MACHINES

▦

▦
node-bCompute
▦
node-cCompute

Three machines make the example easy to follow; they are not a requirement. A controller may be dedicated or also compute. Names are fictional; cluster size and roles depend on your site.

01Inventory & choose roles+

Record CPU topology, RAM, operating system and networking. Choose a reliable controller; it may also run compute work. Keep the first experiment small.

Check: every selected node has a hardware inventory and an agreed role.

02Establish hostname resolution+

Make node names resolve consistently everywhere. Temporary host-file mappings work for an experiment, but DHCP address changes need manual updates.

Check: each node resolves and reaches all peers using their names.

03Align accounts safely+

Provide consistent job-user identities across nodes, through central identity services or coordinated local accounts. Existing IDs do not need changing if already consistent. Preserve recovery access; if migration is necessary, stop affected activity and back up account databases, ownership records and ACLs first.

Check: account identities, file ownership, access groups and recovery login are validated. Identity migration is a maintenance operation, not a mandatory step for every cluster.

04Configure shared authentication+

Check repositories, time synchronization and service identities. In this demonstration, install MUNGE: it creates and verifies tamper-resistant credentials carrying a user's identity, so Slurm services can trust requests across nodes. It does not create user accounts or schedule jobs.

Securely distribute one protected secret key to the participating nodes. Never put that key in documentation or a public repository.

Check: local and cross-node credential decoding succeeds.

05Install consistent Slurm software+

Two common choices on Ubuntu:

Ubuntu packages, with Ubuntu Pro where needed. Install through APT for distribution-integrated packages and updates. Ubuntu Pro is not required just to install Slurm; its ESM Apps coverage can provide additional security fixes for Universe packages such as Slurm. The packaged version may be older but receive backported fixes; check coverage and advisories for your Ubuntu release.

Upstream Slurm from SchedMD. Choose a supported upstream release and follow the official installation guide, preferably building DEB packages on Ubuntu. This gives more control over the version and features, but you manage builds, dependencies and future security updates yourself.

Choose one route consistently across the cluster, deploy compatible versions and install controller/compute components according to each node's role. Keep services from starting prematurely.

Check: versions match and package installation is complete before daemon startup.

06Configure resources & start in stages+

Use Slurm-detected topology to define node resources. Arrange consistent configuration delivery, cgroup isolation and persistent state paths. The demonstration distributes configuration files directly; other deployments may use Slurm's configless mode. Start the controller, then compute daemons, keeping test queues closed until ready.

Check: controller is reachable and every compute node registers with the expected resources.

07Agree on resources, access & priority+

Choose partitions, access rules, limits and scheduling policy. For shared workstations, the demonstration reserves desktop headroom and uses non-preemptive owner queues. Dedicated clusters may instead use accounts, fair-share or other policies. These are choices, not Slurm-wide defaults.

Check: actual resource confinement, permitted/denied access and waiting-job order match the policy you chose.

08Validate small jobs & a real workload+

Run tiny tasks on every node, test permitted and denied submissions, then check a real application's environment and imports. Open normal queues after the agreed limits and scheduling behavior pass. If projects need shared input access, configure and validate per-user shared storage as a separate storage service; Slurm does not provide it.

Check: jobs use the correct identity, node and allocation. A partial application trial does not prove full-run completion or scientific correctness.

09Make reboot recovery persistent+

Enable services at boot, persist normal queue states and configure startup ordering/retries. Agree on automatic node-return policy and test idle reboots individually, controller last.

Check: services start without manual intervention, nodes rejoin, queues retain their intended states and a tiny task runs after each reboot.

10Document everyday operation+

Keep a private deployment record and a separate public/user guide. Provide simple templates, monitoring/cancellation instructions and maintenance expectations. Archive completed setup artifacts without deleting recovery evidence.

Check: users can submit a job without replaying setup scripts or exposing private logs.

ADMINISTRATORS / SHARED STORAGE

One backing store. A private folder per user.

A folder such as ~/Server is a user-facing path to shared storage—not a Slurm queue, not a copy on every node and not an administrator-only archive.

Example architecture, not a live configuration

All names below are fictional. Choose the storage server, backing disk, export paths and identities for your site. Per-user access through NFS and bind mounts is one design; other shared filesystems and layouts are possible.

Example: Alice's single data directory, reached from several machines
LayerExample pathPurpose
Storage server disk/mnt/data/projects/aliceThe actual files. One backing copy.
Central access on each node/srv/projects/aliceLocal bind on the server; NFS access on clients.
Alice's view on every node/home/alice/ServerA bind mount into her directory—not a whole-home export.
01Choose and persist the backing disk+

Audit capacity, filesystem, existing contents and backups. Identify the disk by UUID and verify its boot mount before creating the backing tree. Do not format or repartition a populated disk as part of folder creation.

Check: the real expected disk is mounted. Exports and bind mounts must not silently fall back to an empty directory on the root disk if it is absent.

02Create one private backing directory per user+

Use consistent numeric UID/GID identities across all participating nodes. Give each user ownership of their directory and private permissions, commonly 0700. Provide traversal of the parent without making everyone's files listable. Preserve existing ACLs and content; do not recursively change unrelated homes or datasets.

Check: each ordinary user can access their own folder; a different ordinary user cannot read it. Privacy from peers is not privacy from privileged administrators.

03Configure NFS and restrict network access+

Install the server/client components and select the NFS version. Restrict exports and firewall access to approved clients, retain root squashing and avoid wildcard access. For an NFSv4-only setup, ensure unused legacy RPC services are not needlessly exposed. Review the export options before applying site-specific configuration.

AUTH_SYS relies on trusted client machines and consistent identities. Root squashing is not a security boundary against administrators of trusted clients, and ordinary NFS is not automatically encrypted. Match institutional security requirements.

Check: inspect live exports, actual listening addresses/ports and the dedicated firewall rules. Preserve unrelated rules, including container networking.

04Mount and validate before making it persistent+

Test central client access, then each user's bind path. Protect empty mountpoint stubs against accidental local writes when storage is absent, without claiming they protect against a home-directory owner deliberately replacing a path. Never mount over existing user files without a migration plan.

Check: create a small uniquely named probe as an ordinary user, read the same probe through the other nodes, and verify private access for every enrolled user. Retain or deliberately clean test probes; do not use blanket deletion.

05Add boot persistence and readiness checks+

Use reviewed mount/automount units or fstab entries. Keep dependency order: backing disk → storage service → central access → user bind paths. A systemd automount can trigger its matching mount on first access; put network ordering on the mount, not the automount, to avoid dependency cycles. See the automount reference.

A global network-online.target is not a guarantee that the exact interface/address your server requires is ready. Validate that requirement explicitly, with a bounded wait and a startup timeout that accommodates it. Fail closed if the approved disk, address or firewall is missing; do not simply bypass checks. NetworkManager startup readiness depends on its profiles and device state.

Check: backing filesystem, source, numeric ownership and permissions—not merely that an empty folder or active automount unit exists.

06Test clients first, storage server last+

Arrange a quiet window, exclude affected nodes from new work and let existing work finish. Reboot a client, reconnect and validate storage and Slurm before moving on. Reboot the storage server last while clients stay online; pause shared-folder activity everywhere first. Hard NFS I/O can block during the server outage.

Check: services recover without manual starts; every user's real data path works on every node; permissions remain private; controller/node registration is healthy. Only then release intentional maintenance drains. A check after a manual service start does not prove automatic boot recovery.

07Document outputs, capacity and failure behavior+

Tell users what is shared, what stays local and where each job writes results/scratch. A relative output path follows the execution working directory, not automatically the submission machine. Slurm does not set disk quotas or copy packages. Decide capacity monitoring, quotas, retention and backups separately.

Check: users know the storage server must be available, this is one shared copy rather than a backup, and large outputs have an agreed destination. Deleting a shared file affects the same data seen from other nodes.

Read-only checks for the user's actual data mount

On each Linux node, use an ordinary job account whose site-configured folder is ~/Server. This is not a command to create or share the folder. Stop on a failed or blocked access rather than changing permissions to hide a mount problem.

Trigger access and inspect numeric ownership
stat -c 'path=%n uid=%u gid=%g mode=%a' "$HOME/Server/."

Then inspect the data filesystem at that exact mountpoint. With automounts, filter out the autofs trigger row rather than comparing it with the actual NFS or local bind mount.

Read the actual data mount · adjust filesystem types for your site
findmnt -rn -M "$HOME/Server" -t nfs,nfs4,ext4,xfs,btrfs -o TARGET,SOURCE,FSTYPE,OPTIONS

Compare the source with your site's documented backing/export path and inspect the intended mount flags. Correct numeric ownership alone does not establish the right source or network protection. Never paste private export addresses, keys or internal recovery logs into this public guide.

ADMINISTRATORS / MAINTENANCE

Keep the cluster predictable.

Administrator-led maintenance should protect both Slurm jobs and ordinary desktop work.

BEFORE A REBOOT

Coordinate, exclude, wait.

This is machine maintenance, not folder creation. Check local sessions/background work, block new allocations and let jobs finish. If the machine serves shared storage, coordinate access on every dependent client too. A drained node stays excluded until deliberately restored.

AFTER A REBOOT

Verify before restoring.

Check authentication and compute services, controller connectivity, hostname resolution and node health. Confirm the intended queue states; run a tiny job after safely restoring the node.

WHEN AN ADDRESS CHANGES

Review all address-dependent services.

Update hostname mappings consistently and verify connectivity before changing daemon state. Also review services pinned to numeric addresses, such as NFS listeners, exports, readiness checks and firewall allowlists. Updating hosts alone may not be sufficient.

WHEN SETUP FILES ACCUMULATE

Archive, don't erase.

Keep completed checkpoints, logs and package/build artifacts in a private indexed archive. Preserve ownership and permissions, and record changed paths. Organization is not an independent backup.

Administrator command reference +

Use the real node name and your site's configuration path. These are administrator examples, not an unattended reboot script. DRAIN blocks new allocations; it does not cancel running jobs.

Maintenance exclusion and read-only checks
# Before maintenance: exclude the target, then wait for work to finish.
sudo scontrol update NodeName=node-a State=DRAIN Reason="planned maintenance"
sudo squeue -w node-a

# After maintenance: inspect before deciding whether to restore it.
systemctl is-enabled munge slurmd
systemctl is-active munge slurmd
sudo scontrol ping
sudo scontrol show node node-a
sudo sinfo --all -N -o '%N %P %a %t'

# On the controller node, also check its controller service.
systemctl is-active slurmctld

Only after local health is verified, an administrator may restore a deliberately drained node with sudo scontrol update NodeName=node-a State=RESUME. Do not blindly restore a node with a hardware, identity or configuration failure.

What automatic recovery does—and doesn't—mean

Boot-enabled services and persistent queue states bring the cluster back, not the in-memory state of a running program. A broad automatic-return policy such as ReturnToService=2 can restore a manually DOWN node on valid registration; use deliberate DRAIN maintenance exclusion. Changed DHCP mappings can still prevent recovery.

ADMINISTRATORS / PLANNING

A working base. Room to grow.

This guide's examples use single-node CPU jobs for clarity, not because Slurm is limited to them. Storage, GPUs, distributed applications and accounting may be essential from the start at your site.

  1. 01

    Make projects portable across nodes

    Choose environment replication, containers or shared storage, with code and inputs accessible everywhere a job can run.

  2. 02

    Strengthen ongoing operations

    Stable addressing/DNS, network hardening, off-machine backups, log retention and tested recovery procedures.

  3. 03

    Expand deliberately

    Document new-user and new-node procedures. Add GPU scheduling, scientific multi-node applications or accounting according to your workloads.
