A PRACTICAL GUIDE TO SLURM

One place to queue.

Understand how to set up Slurm, submit jobs and maintain a cluster. General principles first, with a small demonstration to make them concrete.

Three machines make the example easy to follow; they are not a requirement. A controller may be dedicated or also compute. Names are fictional; cluster size and roles depend on your site.

01 / ALLOCATE

Ask for what you need.

CPUs and RAM are reserved for your job. Your program still needs to use the requested workers or threads.

02 / AGREE ON POLICY

Scheduling is a choice.

Access, priority and preemption depend on site policy. Desktop headroom and owner queues are useful options for shared workstations, not universal requirements.

03 / LOCATE YOUR DATA

Know where your files live.

Slurm does not transfer packages or data. Use shared storage or choose a node where the required files and environment are available.

02 / SETUP

The build, in ten steps.

A practical starting sequence, not a universal installation recipe. Adapt the software, identity, storage and scheduling choices to your site.

01Inventory & choose roles+

Record CPU topology, RAM, operating system and networking. Choose a reliable controller; it may also run compute work. Keep the first experiment small.

Check: every selected node has a hardware inventory and an agreed role.

02Establish hostname resolution+

Make node names resolve consistently everywhere. Temporary host-file mappings work for an experiment, but DHCP address changes need manual updates.

Check: each node resolves and reaches all peers using their names.

03Align accounts safely+

Provide consistent job-user identities across nodes, through central identity services or coordinated local accounts. Existing IDs do not need changing if already consistent. Preserve recovery access; if migration is necessary, stop affected activity and back up account databases, ownership records and ACLs first.

Check: account identities, file ownership, access groups and recovery login are validated. Identity migration is a maintenance operation, not a mandatory step for every cluster.

04Configure shared authentication+

Check repositories, time synchronization and service identities. In this demonstration, install MUNGE: it creates and verifies tamper-resistant credentials carrying a user's identity, so Slurm services can trust requests across nodes. It does not create user accounts or schedule jobs.

Securely distribute one protected secret key to the participating nodes. Never put that key in documentation or a public repository.

Check: local and cross-node credential decoding succeeds.

05Install consistent Slurm software+

Two common choices on Ubuntu:

Ubuntu packages, with Ubuntu Pro where needed. Install through APT for distribution-integrated packages and updates. Ubuntu Pro is not required just to install Slurm; its ESM Apps coverage can provide additional security fixes for Universe packages such as Slurm. The packaged version may be older but receive backported fixes; check coverage and advisories for your Ubuntu release.

Upstream Slurm from SchedMD. Choose a supported upstream release and follow the official installation guide, preferably building DEB packages on Ubuntu. This gives more control over the version and features, but you manage builds, dependencies and future security updates yourself.

Choose one route consistently across the cluster, deploy compatible versions and install controller/compute components according to each node's role. Keep services from starting prematurely.

Check: versions match and package installation is complete before daemon startup.

06Configure resources & start in stages+

Use Slurm-detected topology to define node resources. Arrange consistent configuration delivery, cgroup isolation and persistent state paths. The demonstration distributes configuration files directly; other deployments may use Slurm's configless mode. Start the controller, then compute daemons, keeping test queues closed until ready.

Check: controller is reachable and every compute node registers with the expected resources.

07Agree on resources, access & priority+

Choose partitions, access rules, limits and scheduling policy. For shared workstations, the demonstration reserves desktop headroom and uses non-preemptive owner queues. Dedicated clusters may instead use accounts, fair-share or other policies. These are choices, not Slurm-wide defaults.

Check: actual resource confinement, permitted/denied access and waiting-job order match the policy you chose.

08Validate small jobs & a real workload+

Run tiny tasks on every node, test permitted and denied submissions, then check a real application's environment and imports. Open normal queues after the agreed limits and scheduling behavior pass.

Check: jobs use the correct identity, node and allocation. A partial application trial does not prove full-run completion or scientific correctness.

09Make reboot recovery persistent+

Enable services at boot, persist normal queue states and configure startup ordering/retries. Agree on automatic node-return policy and test idle reboots individually, controller last.

Check: services start without manual intervention, nodes rejoin, queues retain their intended states and a tiny task runs after each reboot.

10Document everyday operation+

Keep a private deployment record and a separate public/user guide. Provide simple templates, monitoring/cancellation instructions and maintenance expectations. Archive completed setup artifacts without deleting recovery evidence.

Check: users can submit a job without replaying setup scripts or exposing private logs.

03 / EVERYDAY USE

Create once. Submit when needed.

A batch file describes the allocation and what to run. Log in as your ordinary job user, not the recovery administrator.

Before you start

Examples use node-a, shared, myenv and placeholder paths. Replace them with your site's values. The runner, environment, working directory and inputs must exist on the execution node.

1. Put a batch file beside your Python runner

On the execution node, enter the project directory and create job.sbatch, for example with nano job.sbatch. This example is intentionally guarded until its placeholders are edited.

job.sbatch · Python + Conda
#!/usr/bin/env bash
#SBATCH --job-name=python-project
#SBATCH --partition=shared
#SBATCH --nodelist=node-a
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --mem=4G
#SBATCH --output=slurm-%j.out

set -e
[[ -n ${SLURM_JOB_ID:-} ]] || { echo "Use sbatch, not bash"; exit 1; }
CONDA_BASE=/path/to/conda
CONDA_ENV=myenv
DRIVER=runner.py

[[ -r "$CONDA_BASE/etc/profile.d/conda.sh" && -r "$DRIVER" ]] || {
    echo "Edit the environment and runner paths first"; exit 1;
}
source "$CONDA_BASE/etc/profile.d/conda.sh"
conda activate "$CONDA_ENV"
export OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1
export MKL_NUM_THREADS=1 NUMEXPR_NUM_THREADS=1

srun --mpi=none --ntasks=1 \
    --cpus-per-task="$SLURM_CPUS_PER_TASK" python -u "$DRIVER"
echo "JOB_COMPLETE"
Explain this example, line by line+

The top lines ask Slurm for resources; the remaining lines run inside the allocation. Expand any line or small group below. Blank lines are only for readability.

Customize: queue, node, job label, resources, environment and runner. Usually keep: the submission guard, activation sequence and task launch structure.

01#!/usr/bin/env bash+

Selects Bash as the interpreter. A .sbatch file is a shell script with additional Slurm instructions; the extension itself does not run or schedule it.

02#SBATCH --job-name=python-project+

A readable label shown in job listings. Change it to identify your project; it is not a filename or a Python command.

03#SBATCH --partition=shared+

Selects a partition, often called a queue. Replace shared with a queue you may use at your site. There is no universal queue named shared. If your lab offers an owner queue, selecting it explicitly may provide owner priority.

04#SBATCH --nodelist=node-a+

Pins this example to a particular machine. Replace node-a with the real execution node containing your environment, code and data. Remove this line only when those requirements are available on every eligible node; Slurm can then choose among them.

05–06--nodes=1 · --ntasks=1+

Requests one node and one Slurm task: one launched Python program. That program can create local workers or threads within its CPU allocation. Tasks are not the same as Joblib workers. Changing these numbers alone does not make an ordinary Python program distributed across machines.

07#SBATCH --cpus-per-task=1+

Requests one CPU slot for the task. For a parallel program, increase it and configure the program's worker/thread count accordingly, commonly by reading SLURM_CPUS_PER_TASK. Slots normally refer to logical CPUs, but topology and allocation rules can reserve whole cores. More requested CPUs do not automatically make code faster.

08#SBATCH --mem=4G+

Requests about 4 GiB of total memory per node, not per Python worker. Include the parent process, all workers, arrays and temporary buffers. This is an example estimate; choose a budget for your workload. Exceeding an enforced memory limit can terminate the job.

09#SBATCH --output=slurm-%j.out+

Writes output to a log with the job ID replacing %j, such as slurm-123.out. With no separate error option, standard error normally goes there too. This relative path uses the job's working directory on the execution node; the directory must already exist and be writable.

11set -e+

Makes Bash exit on many ordinary command failures so a failed activation or task does not misleadingly reach JOB_COMPLETE. It is not a complete error-handling framework: shell conditionals and other contexts have exceptions.

12[[ -n ${SLURM_JOB_ID:-} ]] || …+

Checks that a Slurm job ID exists. If not, it prints a message and exits. This helps catch accidentally running bash job.sbatch outside Slurm; it is a convenience check, not a security boundary. Submit using sbatch instead.

13–15CONDA_BASE · CONDA_ENV · DRIVER+

These are shell variables, not Slurm directives. Set CONDA_BASE to the actual Conda installation directory, CONDA_ENV to your environment name, and DRIVER to your Python runner. The runner can be beside this batch file, but execution uses the working directory, not automatically the batch file's original location. Submit from the project folder or specify --chdir.

17–19[[ -r …conda.sh && -r "$DRIVER" ]]+

Checks that the Conda initialization file and Python runner can be read on the chosen node. Otherwise, the block prints a diagnostic and exits with failure. It does not validate every imported package or input file—those must also be available.

20–21source …conda.sh · conda activate …+

Initializes Conda in the batch shell, then activates the requested environment. The job should not depend on whether your interactive terminal currently shows base or another environment. Different environment tools need their own initialization sequence.

22–23export …NUM_THREADS=1+

Limits common numerical libraries to one thread each. This fits the one-CPU example and helps avoid nested threads for multiprocess workloads. For a threaded numerical application, deliberately adjust these values to match the allocation instead of assuming one is always correct.

25–26srun … python -u "$DRIVER"+

srun launches the Python task inside the existing allocation. --ntasks=1 launches one program; --cpus-per-task passes the allocated CPU count to the task. --mpi=none makes clear that this is not an MPI launch. Python -u reduces output buffering so progress appears promptly. The backslash continues the shell command onto the next line; keep it as the last character on that line.

27echo "JOB_COMPLETE"+

Prints a completion marker after the task returns successfully. It shows that this wrapper reached its end, not that scientific results are correct. Preserve the application's logs/results and inspect its own validation messages.

Command-line sbatch options can override matching #SBATCH settings. These examples do not set a time limit; the site's default applies. For full option definitions, see the official sbatch reference.

One CPU and 4 GiB are illustrative starting values, not a universal resource recommendation. No time limit is specified; your site's queue policy determines the default.

2. Check, then submit

From the project directory
bash -n job.sbatch       # Syntax check; does not run Python.
sbatch job.sbatch        # Real submission; runs when allocated.
What do these two commands do? +

bash -n job.sbatch checks Bash syntax without executing the file. It does not validate Slurm options, packages or Python code. No output usually means the shell syntax passed.

sbatch job.sbatch submits one job to the scheduler. A returned job ID means accepted, not necessarily started or completed. Repeating sbatch submits another job; do not resubmit just because the first is waiting.

sbatch returns a job ID. It transfers the batch script, not your project files. The default working directory is the submission directory, and the log appears on the execution node. You do not need to make the file executable or activate Conda in your login shell.

If your installation requires an explicit configuration path, prefix commands with env SLURM_CONF=/etc/slurm/slurm.conf. Keep #SBATCH directives before executable commands; shell variables are not expanded in those directives.

3. Monitor and read the log

Replace 123 with your job ID
squeue -u "$USER"             # Your waiting/running jobs.
scontrol show job 123         # Allocation and output paths.
tail -f slurm-123.out         # Watch output; Ctrl+C stops watching.
scancel 123                  # Deliberately cancel this job.
Explain monitoring and cancellation +

squeue -u "$USER" filters waiting/running jobs to your login user. PENDING means waiting for allocation; RUNNING means execution; COMPLETING means cleanup.

scontrol show job 123 reads that job's current details, including requested resources, working/output paths and state. Completed records may later expire.

tail -f slurm-123.out follows new log lines on the machine containing the log. Ctrl+C exits the viewer; it does not cancel the job.

scancel 123 cancels that specific job. It changes state and may lose unfinished work: only use it deliberately, with your actual job ID. It is not a monitoring command.

A job disappearing from the queue is not proof of success. Read its completion/error messages and, while the record is retained, its job state and exit code. Cancellation can lose unfinished work. Persistent accounting is a separate feature; keep important logs and results.

RESOURCE REQUESTS

Allocation ≠ parallelism

For one local parallel Python program, usually request one task with multiple CPUs. Configure its worker count from SLURM_CPUS_PER_TASK; requesting four CPUs alone does not create four workers. Memory is the total per-node reservation, including all workers.

OWNER QUEUES

Priority is an explicit choice

If your site offers an owner queue, submit to that queue to use it. Owner identity does not automatically raise a shared-queue job's tier. With non-preemption, an owner may still wait for a running guest.

04 / MAINTENANCE

Keep the cluster predictable.

Administrator-led maintenance should protect both Slurm jobs and ordinary desktop work.

BEFORE A REBOOT

Coordinate, exclude, wait.

Agree on a maintenance window. Check local sessions and background work, prevent new allocations to the target, and let existing jobs finish. A drained node stays excluded until deliberately restored.

AFTER A REBOOT

Verify before restoring.

Check authentication and compute services, controller connectivity, hostname resolution and node health. Confirm the intended queue states; run a tiny job after safely restoring the node.

WHEN AN ADDRESS CHANGES

Repair name resolution.

Update the affected hostname mapping consistently on all nodes. Verify resolution and connectivity before changing daemon state. Slurm configurations using names usually need no IP edit or reinstall.

WHEN SETUP FILES ACCUMULATE

Archive, don't erase.

Keep completed checkpoints, logs and package/build artifacts in a private indexed archive. Preserve ownership and permissions, and record changed paths. Organization is not an independent backup.

Administrator command reference +

Use the real node name and your site's configuration path. These are administrator examples, not an unattended reboot script. DRAIN blocks new allocations; it does not cancel running jobs.

Maintenance exclusion and read-only checks
# Before maintenance: exclude the target, then wait for work to finish.
sudo scontrol update NodeName=node-a State=DRAIN Reason="planned maintenance"
sudo squeue -w node-a

# After maintenance: inspect before deciding whether to restore it.
systemctl is-enabled munge slurmd
systemctl is-active munge slurmd
sudo scontrol ping
sudo scontrol show node node-a
sudo sinfo --all -N -o '%N %P %a %t'

# On the controller node, also check its controller service.
systemctl is-active slurmctld

Only after local health is verified, an administrator may restore a deliberately drained node with sudo scontrol update NodeName=node-a State=RESUME. Do not blindly restore a node with a hardware, identity or configuration failure.

What automatic recovery does—and doesn't—mean

Boot-enabled services and persistent queue states bring the cluster back, not the in-memory state of a running program. A broad automatic-return policy such as ReturnToService=2 can restore a manually DOWN node on valid registration; use deliberate DRAIN maintenance exclusion. Changed DHCP mappings can still prevent recovery.

05 / WHAT COMES NEXT

A working base. Room to grow.

This guide's examples use single-node CPU jobs for clarity, not because Slurm is limited to them. Storage, GPUs, distributed applications and accounting may be essential from the start at your site.

  1. 01

    Make projects portable across nodes

    Choose environment replication, containers or shared storage, with code and inputs accessible everywhere a job can run.

  2. 02

    Strengthen ongoing operations

    Stable addressing/DNS, network hardening, off-machine backups, log retention and tested recovery procedures.

  3. 03

    Expand deliberately

    Document new-user and new-node procedures. Add GPU scheduling, scientific multi-node applications or accounting according to your workloads.
