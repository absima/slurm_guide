02 / YOUR PYTHON SCRIPT

A random estimate of π.

Sample points uniformly from the square [0, 1] × [0, 1]. Count those whose distance from the origin (0, 0) is at most one. The region we count is a quarter of the unit disk, centred at the square's bottom-left corner.

Why does counting points estimate π?

  1. Specify the geometry. The square has side length 1 and area 1. The full disk x² + y² ≤ 1 has radius 1, centre (0, 0) and area π.
  2. Take its first-quadrant part. Inside our square, that disk occupies a quarter-disk of area π/4. Its curved boundary is the arc x² + y² = 1, from (1, 0) to (0, 1).
  3. Use uniform sampling. Draw X and Y independently, each uniformly on [0, 1]. The probability that the sampled point lies in the quarter-disk equals the area ratio: P(X² + Y² ≤ 1) = (π/4) / 1 = π/4.
  4. Estimate that probability. If N_inside of N points satisfy the inequality, then N_inside / N estimates π/4. Therefore π̂ = 4 × N_inside / N.

“Quarter-disk” means the filled region; “quarter-circle” means the curved arc, not the filled region. The area identity is exact. The approximation comes from replacing a probability with a finite sample fraction.

SAMPLES

Points in one trial

samples = 10000 draws 10,000 points per trial. The test x*x + y*y <= 1 counts the points inside the quarter-disk.

REALISATIONS

Repeat the experiment

realisations = 5 repeats the experiment five times. We pool the hits from all 50,000 points to estimate π. Change these two settings when you need more work.

Tell Slurm what to run.

Python contains the calculation. The batch file requests resources and runs it when those resources are allocated.

nano job.sbatch

Edit before submitting

Replace node-a with the real compute machine containing your project folder. Use a queue you can access instead of shared if necessary. Submit as your own job user, without sudo. Both files must be available in the project directory on that machine.

Which lines matter, and why?+
#SBATCH --partition · --nodelist+

Choose an allowed queue and the machine containing the project. Slurm transfers the batch file, not neighboring Python or input files.

--nodes=1 · --ntasks=1 · --cpus-per-task=1+

One machine, one Python task, one CPU slot. This code is serial: more requested CPUs do not create workers.

--mem=1G · --time=00:10:00+

Request 1 GiB total RAM and a ten-minute job deadline. These are teaching choices, not lab-wide limits. Slurm may stop the job at the deadline or if it exceeds enforced memory limits.

--job-name · --output=slurm-pi-%j.out+

The name labels your job; %j becomes its job ID in the log filename. Printed output and ordinary errors go into that log.

srun python3 myscript.py+

Launch the calculation using Python 3, inside Slurm's allocated resources.

set -e · JOB_START · JOB_COMPLETE+

The echo lines mark the beginning and successful end in the log. set -e stops this simple script if environment setup or srun fails, so it does not falsely print JOB_COMPLETE. Slurm supplies $SLURM_JOB_ID; hostname reports the execution machine.

The π calculation uses only standard Python 3. No Conda setup is needed for this example. If your project uses a Conda environment, see the optional addition below.

Submit from the project directory: Slurm uses that directory by default.

Optional: use your Conda environment +

If your code needs packages from a Conda environment, add these two lines just before the srun line in your batch file:

Optional environment setup
source "/path/to/conda/etc/profile.d/conda.sh"
conda activate mypyenv

Replace mypyenv with your own environment name and /path/to/conda with your installation path. Run conda info --base in a Conda-enabled terminal to find that path. After activation, use srun python myscript.py to select the environment's Python. The environment and packages must already be accessible on the execution machine; activation does not install them.

You can use the same addition in the array batch file; keep its array-index argument.

04 / CHECK BEFORE CALCULATING

Check, then run.

Keep the first check small. Passing a syntax check does not prove a future analysis will work or fit in memory.

A. Check the Bash syntax

No submission or execution
bash -n job.sbatch

Silence normally means the shell syntax passed. This does not run Python or validate Slurm's resource options.

B. Ask Slurm to check the resource request

Scheduler check · no calculation submitted
sbatch --test-only job.sbatch

This checks the request with Slurm without submitting a real job. It does not execute the batch file, activate Conda or test your Python code. A small real run is still needed. See the sbatch reference.

Optional: add a Python syntax-check mode +

The simple batch file above runs the calculation directly. If you want a separate check-only job, insert this snippet immediately before the srun calculation line, after JOB_START (and any optional environment setup):

Optional addition to job.sbatch
if [[ ${1:-} == --check-only ]]; then
    srun python3 -m py_compile myscript.py
    echo CHECK_ONLY_OK
    exit 0
fi

Only after adding that snippet, submit the check as:

A real, small Slurm job · snippet required
sbatch --time=00:02:00 job.sbatch --check-only

Read its slurm-pi-JOBID.out log. Expect CHECK_ONLY_OK, without trial results or JOB_COMPLETE: the snippet exits before the calculation. It may create __pycache__. This checks syntax, not imports, inputs or scientific correctness. --check-only is our optional script argument, not a Slurm option. Without the snippet, it does not skip the calculation. No --run argument is needed for normal submissions.

05 / SUBMIT THE CALCULATION

Now let it compute.

After checking the request, submit a small calculation using the same two files.

Runs the workload set in myscript.py
sbatch job.sbatch

Slurm returns a new job ID. Accepted does not mean started or completed; the job may wait. Repeating sbatch submits another job, not a connection to the first.

If your run ID is 124, its printed estimates and errors are in slurm-pi-124.out. There is no separate JSON/result file to manage.

Read the result · replace 124 with your job ID
cat slurm-pi-124.out

Look for the trial estimates, COUNTS, SIMULATION_COMPLETE and JOB_COMPLETE. The log is in the project directory on the execution node, not automatically on your laptop. You may disconnect after submitting; do not reboot the compute machine.

06 / EVERYDAY COMMANDS

Watch. Inspect. Stop deliberately.

Run these individually from your cluster terminal. Replace 124 and the log filename with your current job's values.

Your queued and running jobs

Read-only
squeue -u "$USER"

PD means pending; the reason explains why it is waiting. R means running. CG means completing/cleanup. A short example may finish before you check. Do not resubmit just because it is pending.

Which machine, resources and paths?

Read-only · job records may expire
scontrol show job 124

Inspect JobState, NodeList, CPU/memory requests, WorkDir, StdOut and ExitCode. JOB_START host=… in the log also records where Python ran.

Follow progress live

Ctrl+C exits the viewer, not the job
tail -f slurm-pi-124.out

Look for the Trial … pi estimate lines, SIMULATION_COMPLETE and JOB_COMPLETE. Leaving squeue alone does not prove success: cancellation, timeout and failure also remove jobs. Preserve logs; persistent accounting commands such as sacct depend on site configuration.

Cancel your job

Changes state · only your intended job
scancel 124

This stops the computation. The log may contain partial progress, but this example has no checkpoint/resume support; a cancelled run is not a completed result. Do not use sudo, broad cancellation commands or kill another user's processes.

Common first-job errors +

Invalid node/partition: edit the fictional values and confirm queue access with your lab. Unable to open batch file: check your directory and whether both files reached the cluster. Python/file missing on the node: fix that node's environment/path; a same-named local folder elsewhere is not shared automatically.

No log yet: the job may still be pending. CHECK_ONLY_OK but no simulation: the optional check-only snippet skipped the calculation; submit without --check-only to calculate. Config discovery error: use your site's instructions; some installations require env SLURM_CONF=/etc/slurm/slurm.conf before Slurm commands.

07 / TURN UP THE WORKLOAD

Change two numbers.

Increase the settings at the top of myscript.py when you are ready for a heavier calculation.

Edit these Python lines in myscript.py · not terminal commands
realisations = 200
samples = 1000000

This draws 200 million points instead of the small default 50,000. Runtime depends on the machine and Python version. It processes points one at a time, so it does not need to store a giant array in RAM.

Save the file, then submit with the same command:

Slurm runs the new settings
sbatch job.sbatch

Do not edit the Python file while an earlier job is waiting to read it. The ten-minute tutorial deadline still applies; estimate runtime with a small trial before deliberately requesting a longer deadline. After increasing these values, do not run the calculation directly in your login terminal.

More requested CPUs do not parallelize a loop

The calculation still uses one CPU. More CPUs need actual workers or threads; several nodes need separate jobs/arrays or distributed code. Neither changing --cpus-per-task nor --nodes creates that logic.

08 / USE AVAILABLE COMPUTE NODES

Run independent parts.

The π estimator stays the same. A job array runs the same short script with different part numbers, so each job draws different random points. Each part still runs on one node and one CPU.

Make the files accessible first

Put myscript.py and job-array.sbatch in an approved shared project folder available at the same path on every eligible node, and submit from there. A site-configured ~/Server may provide this; simply creating a folder called Server does not. Python 3 must be available on each eligible node. If you add Conda setup, your chosen environment must also be accessible there. The small job logs in this lesson also go into the shared project folder.

A. The same Python script, one extra argument

The first lesson uses part = 0. For arrays, the batch file passes the index as an argument. The small sys.argv block reads it; 42 + part * realisations + trial assigns a distinct seed to each trial. Python still knows nothing about machine names or Slurm.

With the default five realisations, part 0 uses seeds 42–46, part 1 uses 47–51, and so on. Every part prints its estimate and a COUNTS inside sampled line using exactly the same counting formula.

B. Save the array batch file

Save this beside myscript.py. Use a real queue that includes your intended nodes. This example deliberately omits the first job's nodelist pin.

job-array.sbatch+
job-array.sbatch · edit the queue if needed

--array=0-5%3 creates six parts, with at most three running at once. The CPU/RAM request applies to each part. Slurm supplies SLURM_ARRAY_TASK_ID; the srun line passes it to Python. %A_%a gives every part a separate log using the array ID and index.

Three concurrent jobs does not mean three nodes

Slurm may use different nodes or place several parts on one machine. %3 is a concurrency limit, not a placement rule. Busy/ineligible nodes may not be used. For a small calculation, queue and startup overhead can outweigh parallel speedup.

C. Check, submit and inspect

Check the shell syntax
bash -n job-array.sbatch
Check the array's scheduler request · no job submitted
sbatch --test-only job-array.sbatch

As before, this does not run Python or test the environment. Keep the first real array small, and inspect the logs.

Submit all six calculation parts
sbatch job-array.sbatch

If the run's array ID is 200, use your actual ID in these commands:

One row per part · inspect its node
squeue -r -j 200 -o '%.18i %.9T %.20N %R'
Read part 0's calculation
cat slurm-pi-array-200_0.out

Read the other parts in the same way. ARRAY_START … host=… records the execution machine. Each successful run has trial estimates, COUNTS, SIMULATION_COMPLETE and ARRAY_COMPLETE. You can stop here: independent simulations with separate results are already a useful array workflow.

D. Optional: combine the results with a short Python script+

To obtain one estimate using all parts, add their hit counts K and sample counts N, then compute 4 × ΣK / ΣN. This is the same π estimator, now using points from several jobs.

Save the commented helper beside your logs. It reads the COUNTS lines directly; there are no JSON files to manage. Its basic checks require the expected number of different logs and a completed calculation in each.

Optional: deliberately use three different nodes +

Replace the fictional node names with real compute machines. These commands submit one part per node in three separate single-element arrays; each has its own ID. The shared code must be available on all three. A pinned job may wait if that machine is busy.

Part 0 · first node
sbatch --array=0 --nodelist=node-a job-array.sbatch

E. Cancel deliberately

Cancel the remaining parts · replace 200
scancel 200

Use scancel 200_2 to cancel only part 2 instead. Cancellation may leave partial logs; this example has no checkpoint/resume support.

See the Slurm job-array guide for index ranges, concurrency limits and identifiers. The same pattern applies to independent subjects, parameter combinations or repeated simulations.

09 / YOUR OWN PROJECT

Keep the workflow. Change the calculation.

You have used the same myscript.py for the single-node and job-array examples. Use those patterns for your own analysis instead of starting a separate submission system.

01Point the batch file to your runner+

Replace myscript.py with your real runner and adapt its arguments/output paths. Keep code, inputs and environment available on every eligible execution node, or pin to a node containing them. Slurm copies the batch file, not the rest of your project.

02Initialize the environment inside the job+

The default batch example uses system Python 3. If your analysis needs a Conda environment, add the optional setup shown in section 3 before srun. Do not rely on whichever environment happens to be active in your login terminal.

For Conda, add these two lines and adapt both placeholders to your installation/environment. They belong inside your batch file, not in a new Python example:

Optional addition before srun
source "/path/to/conda/etc/profile.d/conda.sh"
conda activate mypyenv

For a virtual environment, use its Python executable or the site's documented activation method. Replace mypyenv with your own environment name. Use srun python after activation. The environment must exist on the node where the job runs.

03Implement a genuine lightweight check+

The optional snippet in section 4 adds --check-only by compiling Python, not executing it. The basic batch file has no custom modes. Compilation tests syntax only. For a real project, add deliberate lightweight checks for imports, inputs, settings and output paths before heavy work; passing a syntax check is not a full application validation.

04Measure before requesting more+

Start with a small input. Request total memory including workers/buffers and a suitable runtime budget. Our serial demo uses one CPU; additional CPUs need actual parallel code. Multiple nodes need independent jobs/arrays or a distributed program, not just a larger node request.

05Keep results separate and coordinate shared use+

Give concurrent runs separate logs, results and scratch paths. Output is written where the execution program directs it; shared inputs do not imply every output should go onto shared storage. Follow local queue/workstation-priority rules and coordinate maintenance. Slurm user commands do not need sudo.

Your reusable sequence

Prepare → write Python → request resources → check → submit → monitor → inspect results. Ask your lab for its real queue/node names, storage layout, environment instructions and support contacts; these are site-specific.
